Caso de Uso UC1: Ver Panel de Préstamos Activos
Resumen:  El encargado puede ver en la pantalla principal una lista de todo lo que está
prestado y aún no se devolvió.
Actores:  Encargado (primario), Sistema (secundario).
Metas:  El encargado quiere saber rápido qué herramientas faltan en el inventario para poder
controlarlas antes de irse.
Precondiciones:  El encargado inició sesión en el sistema.
Poscondiciones:  El sistema muestra una lista al día con los equipos que faltan devolver.
Escenario Principal (Paso a paso):
El encargado entra a la pantalla principal.
El sistema busca en la base de datos todos los equipos que figuran como "prestados".
El sistema muestra la lista en pantalla con el nombre de quién lo tiene.
Flujos Alternativos (Posibles errores):
A1 - No hay préstamos:  Si todo está devuelto, el sistema muestra un mensaje diciendo "El
inventario está completo, no hay préstamos activos".
Caso de Uso UC2: Registrar Préstamo a Alumno
Resumen:  Sirve para anotar que un alumno se llevó una herramienta, dejando registrado qué
profesor le dio permiso.
Actores:  Encargado (primario), Sistema (secundario).
Metas:  Entregar la herramienta rápido para que no se armen filas y dejar claro quién es el
responsable.
Precondiciones:  El encargado inició sesión. La herramienta está disponible.
Poscondiciones:  Queda anotado el préstamo y la herramienta pasa a figurar como "Prestada".
Escenario Principal (Paso a paso):
El encargado hace clic en "Nuevo Préstamo".
El sistema le pide que lea el código de barras de la herramienta.
El encargado escanea la herramienta.1.

Caso de Uso UC3: Registrar Préstamo a Docente (Por Lote)
Resumen:  Permite anotar de una sola vez varias herramientas que se lleva un profesor para su
clase.
Actores:  Encargado (primario), Sistema (secundario).
Precondiciones:  El encargado inició sesión. Las herramientas están disponibles.
Poscondiciones:  Quedan anotados todos los equipos a nombre del profesor y pasan a figurar
como "Prestados".
Escenario Principal (Paso a paso):
El encargado hace clic en "Préstamo por Lote".
Escribe el nombre del profesor.
El encargado escanea uno por uno todos los códigos de barras de las herramientas.
El sistema muestra la lista de todo lo escaneado.
El encargado confirma que la lista está bien.
El sistema guarda el préstamo de todas las herramientas juntas.

Precondiciones:  El proyector existe en el sistema.
Poscondiciones:  Queda guardada la reserva y nadie más puede pedir el proyector en ese
horario.
Escenario Principal (Paso a paso):
El encargado entra a la sección "Proyectores".
El sistema muestra un calendario con los horarios libres y ocupados.
El encargado elige un proyector, un horario y anota al profesor.
El sistema guarda la reserva y bloquea ese horario.4.

Caso de Uso UC5: Escanear Código de Barras
Resumen:  Sirve para escanear cualquier herramienta perdida o suelta y saber al instante de
dónde es y si debería estar prestada.
Actores:  Encargado (primario), Sistema (secundario).
Poscondiciones:  El sistema muestra la ficha técnica de la herramienta.
Escenario Principal (Paso a paso):
El encargado hace clic en "Consulta Rápida".
Escanea la herramienta.

Prestado/Roto).
Flujos Alternativos (Posibles errores):
A1 - Código no existe:  Si escanea algo que no es del colegio, el sistema avisa que no lo
encuentra en el inventario.
Caso de Uso UC6: Registrar Devolución
Resumen:  Sirve para anotar que devolvieron una herramienta, liberando al profesor o alumno
de la responsabilidad.
Actores:  Encargado (primario), Sistema (secundario).
Precondiciones:  La herramienta figura como "Prestada".
Poscondiciones:  El préstamo se cierra y la herramienta vuelve a estar "Disponible".
Escenario Principal (Paso a paso):
El encargado hace clic en "Devolución".
Escanea la herramienta que le acaban de entregar.
El sistema muestra quién la tenía y pregunta si está en buen estado.
El encargado elige "Buen estado" y confirma.
El sistema cierra el préstamo.

 ​ Cuestionario de Relevamiento de Requisitos ​ 1. Sobre el proceso actual ​ Pregunta: ¿Cómo se realiza el proceso de devolución y verificación del estado de la herramienta? ​ Respuesta: No es un control tan estricto. Sin embargo, lo de más valor sí se anota y se revisa que no tenga nada dañado al ser devuelto. ​ Pregunta: ¿Cómo se gestionan los préstamos que son para otro turno? ​ Respuesta: Hay que buscar la forma de comunicar los préstamos activos de un turno a otro. ​ Pregunta: ¿Qué áreas del establecimiento van a utilizar el sistema? ​ Respuesta: El área técnica y la biblioteca necesitan el sistema. El alcance quedaría solo para el colegio, no para la universidad. ​ 2. Sobre la estructura de datos ​ Pregunta: ¿Qué información es obligatoria registrar al momento de prestar un equipo? ​ Respuesta: El nombre y curso en el que estaba el alumno, y el nombre del docente. ​ Pregunta: ¿Cómo se debe registrar cuando un profesor se lleva varios objetos a la vez? ​ Respuesta: Para llevar en cantidad, se anota el profesor, la cantidad y la identificación de cada uno de los objetos. ​ 3. Sobre la identificación y el inventario ​ Pregunta: ¿Cómo identifican internamente cada herramienta o equipo? ​ Respuesta: Actualmente no tienen nada. Se necesita implementar una identificación con códigos de barras. ​ Pregunta: ¿Es necesario saber dónde están guardadas las cosas? ​ Respuesta: Sí, se necesita un inventario de todas las máquinas del colegio y organizarlas por lugar (dónde están). ​ Pregunta: ¿El sistema debe diferenciar de qué sector es cada cosa? ​ Respuesta: Sí, tiene que haber algo que marque que el objeto está en la biblioteca, por ejemplo. ​ 4. Sobre las reglas de negocio ​ Pregunta: ¿Existe un límite de cantidad de herramientas o equipos que una misma persona puede tener a préstamo simultáneamente? ​ Respuesta: No existe. ​ Pregunta: ¿Hay herramientas específicas que requieran autorización especial para ser prestadas a los alumnos? ​ Respuesta: No hay, pero se necesita la identificación de los profesores en el sistema para avalar a los alumnos que van a buscar algún objeto. ​ Pregunta: ¿Hay algún equipo que requiera un control distinto al resto? ​ Respuesta: Sí, se necesita una sección aparte para los proyectores, ya que es lo que más genera conflicto. ​ 5. Sobre las excepciones y problemas ​ Pregunta: ¿Qué procedimiento se sigue si un alumno o profesor devuelve una herramienta dañada? ​ Respuesta: Debería haber un registro en el sistema para saberlo. ​ Pregunta: ¿Qué sucede si llega el final del día o del turno y hay elementos que figuran como prestados pero no fueron devueltos? ​ Respuesta: Actualmente se busca manualmente dónde está. ​ 6. Sobre los reportes y la usabilidad ​ Pregunta: Al abrir el sistema al comienzo de tu jornada, ¿cuál es la información más urgente que necesitas ver en la pantalla principal? ​ Respuesta: Una pantalla que muestre la lista de préstamos activos. ​ Pregunta: ¿Necesitas generar algún tipo de reporte para presentar a los directivos? ​ Respuesta: Que se genere un botón que permita exportar los datos a Excel o PDF. ​ Historia de Usuario ​ Como encargado de biblioteca o área técnica, quiero ver una lista de los préstamos activos en la pantalla principal, para identificar rápidamente qué herramientas no fueron devueltas antes de finalizar mi turno.

 Análisis Estratégico y Gestión de Riesgos Institución: Escuela Normal Superior Dalmacio Vélez Sarsfield Carrera: Tecnicatura Superior en Desarrollo de Software Asignaturas: Ingeniería del Software Proyecto: Sistema de control de prestaciones de área técnica 4.1 Matriz FODA Aplicada al Proyecto TI El siguiente análisis evalúa la viabilidad del proyecto, considerando tanto la capacidad técnica del equipo interno como el contexto y las condiciones del establecimiento educativo. Análisis Interno (Equipo y Producto) Análisis Externo (Contexto y Entorno) Fortalezas Acceso directo a usuarios: El equipo tiene contacto inmediato con los stakeholders principales (encargados, docentes) por pertenecer a la misma institución. Roles definidos: El equipo cuenta con una estructura multidisciplinaria clara para abarcar análisis, diseño, desarrollo y control de calidad. Conocimiento del problema: Comprensión profunda del proceso manual actual y sus deficiencias (pérdida de trazabilidad entre turnos). Oportunidades Digitalización institucional: Primer paso para modernizar los procesos de la escuela que actualmente funcionan en papel. Integración tecnológica: Posibilidad de incorporar escaneo de códigos de barras para agilizar entregas y recepciones. Escalabilidad: Un sistema exitoso en el área técnica y biblioteca puede ser adaptado posteriormente a otras áreas de la institución. Debilidades Presupuesto nulo: El proyecto depende enteramente de herramientas gratuitas, de código abierto o desarrollo propio, sin fondos para licencias de software o hardware adicional. Restricción temporal: Plazo estricto de desarrollo de 3 meses que limita la cantidad de funcionalidades (features) que se pueden incluir en la primera versión. Amenazas Resistencia al cambio: Riesgo de que los encargados del área técnica boicoteen el sistema y decidan continuar operando de forma verbal o en papel. Infraestructura de hardware: Fallos en la red del colegio o en la computadora de la biblioteca que impidan el acceso al sistema en momentos críticos de cambio de turno. 4.2 Matriz de Riesgos (Impacto / Probabilidad) Para garantizar el éxito y la continuidad del software, se han identificado los siguientes riesgos metodológicos y técnicos, evaluados según su probabilidad de ocurrencia y el nivel de impacto sobre el proyecto, junto con sus planes de mitigación. Riesgo Potencial Probabilidad Impacto Plan de Mitigación (Acción Preventiva / Reactiva) Boicot o rechazo por parte del usuario principal: El encargado de área técnica se niega a utilizar el software por considerarlo más lento que anotar en papel. Media Alto Mitigación: Involucrar activamente al usuario en el prototipado (UI/UX). Diseñar una interfaz minimalista, con un panel principal de acceso rápido, y asegurar que cargar un préstamo tome menos clics y tiempo que escribirlo a mano. Pérdida de datos e historial de préstamos: Falla del servidor local, corte de energía prolongado o corrupción de la base de datos que borre los préstamos activos. Baja Alto Mitigación: Configurar respaldos (backups) automáticos de la base de datos. Si la arquitectura lo permite, alojar el sistema en la nube o mantener un registro redundante exportable (HU09). Desviación del cronograma (Scope Creep): Retrasos en el desarrollo que impidan finalizar el sistema operativo en el plazo exigido de 3 meses. Media Medio Mitigación: Utilizar metodologías ágiles dividiendo el desarrollo en Sprints. Enfocarse estrictamente en construir primero el MVP (Producto Mínimo Viable) con las Épicas 1 y 2, dejando reportes complejos para el final. Fallo en la integración del lector de código de barras: Incompatibilidad de hardware o dificultad técnica para escanear las herramientas rápidamente. Media Medio Mitigación: Desarrollar el sistema con una funcionalidad de búsqueda predictiva (autocompletado por teclado) como método principal o de contingencia, asegurando que el sistema no dependa exclusivamente del escáner. Problemas de Accesibilidad y Usabilidad (WCAG): La interfaz resulta ilegible o cansadora para los usuarios durante turnos largos, dificultando la transición rápida. Baja Medio Mitigación: Aplicar estrictamente normas de alto contraste visual desde el diseño inicial. Implementar navegación completa por teclado (Tab, Enter) para no depender del mouse en la carga de formularios repetitivos.

 Entregable Módulo 3: Ingeniería de Requisitos y Filosofía Ágil Institución: Escuela Normal Superior Dalmacio Vélez Sarsfield Carrera: Tecnicatura Superior en Desarrollo de Software Asignaturas: Programación III, Ingeniería del Software Docente: Prof. Juan Tortelli 1. Características de los Usuarios (Stakeholders) A partir del relevamiento cualitativo y cuantitativo realizado, se identifican los siguientes actores que interactuarán directa o indirectamente con el sistema de gestión de inventario: Encargados de Biblioteca y Área Técnica (Usuarios Principales): Son quienes operarán el sistema diariamente en el colegio. Su principal necesidad es mantener el control del inventario, gestionar las transacciones con agilidad y evitar la pérdida de información durante los cambios de turno. Docentes (Usuarios Secundarios / Facilitadores): Retiran equipos para sus clases (a menudo en cantidad). Además, actúan como responsables al avalar a los alumnos que retiran herramientas en su nombre. Alumnos (Usuarios Indirectos): Son los beneficiarios finales de muchas de las herramientas prestadas. Se requiere registrar su nombre y curso, bajo la autorización de un docente, sin que ellos operen el sistema de forma directa. Directivos (Patrocinadores / Consumidores de Información): No operan el sistema en el día a día, pero requieren visualizar reportes exportables sobre el uso y estado general del inventario del establecimiento. 2. Matriz de Poder-Interés Para priorizar los esfuerzos y la comunicación durante el desarrollo, los stakeholders se clasifican de la siguiente manera: Nivel de Interés Bajo Poder Alto Poder Alto Interés Mantener Informados: Docentes: Necesitan que el proceso de préstamo sea ágil para no perder tiempo de clase. Gestionar de Cerca: Encargados de Biblioteca y Área Técnica: El éxito del sistema depende de su adopción; sus requerimientos de usabilidad son críticos. Bajo Interés Monitorear: Alumnos: Solo interactúan tangencialmente al solicitar el préstamo de forma presencial. Mantener Satisfechos: Directivos: Requerirán reportes periódicos en formatos estándar para la toma de decisiones institucionales. 3. Backlog Inicial (Historias de Usuario) Este backlog traduce los hallazgos en requisitos funcionales y no funcionales, priorizados por el valor aportado a la gestión del inventario y redactados bajo la estructura ágil estándar. Épica 1: Gestión Diaria y Transacciones 1 - Panel de Préstamos Activos: Como encargado de biblioteca o área técnica, quiero ver una lista de los préstamos activos en la pantalla principal, para identificar rápidamente qué herramientas no fueron devueltas antes de finalizar mi turno. 2 - Préstamo Individual (Alumno): Como encargado, quiero registrar un préstamo ingresando el nombre del alumno, su curso y el docente que lo avala, para mantener la responsabilidad y trazabilidad de la herramienta entregada. 3 - Préstamo por Lote (Docentes): Como encargado, quiero asignar múltiples objetos simultáneamente a un docente registrado, especificando la cantidad y la identificación de cada objeto, para agilizar la entrega de materiales al inicio de una clase. 4 - Módulo Exclusivo de Proyectores: Como encargado, quiero gestionar las reservas y préstamos de los proyectores en una sección destacada e independiente dentro del sistema, para tener un control riguroso sobre estos equipos de alta criticidad y demanda. Épica 2: Control de Inventario e Identificación 5 - Identificación por Código de Barras: Como encargado, quiero poder escanear e identificar cada herramienta o equipo mediante códigos de barras, para que el proceso de registro de entrada y salida sea instantáneo y sin errores manuales. 6 - Ubicación y Sectorización: Como encargado, quiero visualizar en el sistema a qué sector (ej. biblioteca, área técnica) y ubicación física específica pertenece cada objeto, para saber exactamente de dónde sacarlo y dónde guardarlo tras su devolución. Épica 3: Seguimiento, Excepciones y Reportes 7 - Registro de Daños: Como encargado, quiero disponer de una opción para marcar un ítem como &quot;dañado&quot; al momento de registrar su devolución, para mantener un registro histórico y documentado de las roturas. 8 - Trazabilidad entre Turnos: Como encargado, quiero que el sistema refleje automáticamente el estado de los préstamos no devueltos al usuario del siguiente turno, para garantizar la continuidad del control sin depender de comunicación informal. 9 - Exportación de Reportes: Como directivo o encargado, quiero presionar un botón que permita exportar los datos de inventario y préstamos a formato Excel o PDF, para presentar informes de estado formales a las autoridades del colegio. Épica 4: Accesibilidad y Requisitos No Funcionales (RNF) 10 - Navegación Accesible y Ágil (WCAG): Como usuario del sistema, quiero poder navegar por todos los formularios de préstamo y devolución utilizando únicamente el teclado y contando con alto contraste visual, para garantizar la accesibilidad, mitigar la fatiga visual y acelerar la carga de datos en momentos de alta concurrencia.
